# LegalMCP cloud

Claude orchestrates; OpenAI is the opponent; Gemini and DeepSeek independently review; Grok is a separate creative critic (advertising, positioning, copy, scenarios) that is NOT part of the default legal/code chain. Official legal sources outrank model agreement.

Project MCP configuration launches this server inside a single-repository Claude Code cloud session. SessionStart installs dependencies only when CLAUDE_CODE_REMOTE=true. Bash scripts use Linux line endings. Setup is locked and cached by requirements hash.

Cloud proxy-auth mode (explicit opt-in). In a cloud session the provider keys live only in the network proxy (Network secrets) and are never in the environment, while the OpenAI, Gemini and DeepSeek SDKs refuse to build a client without an api_key. launch.sh turns it on by default in a cloud session: when CLAUDE_CODE_REMOTE=true and LEGALMCP_PROXY_AUTH is not set at all (neither in the environment nor as a line in .env) it exports LEGALMCP_PROXY_AUTH=1. Any explicit value, including 0 or an empty string, is respected, so the mode can still be disabled; outside the cloud nothing changes. You can also set the plain, non-secret variable yourself (cloud environment variables, or .env; never a key). The mode is active only when LEGALMCP_PROXY_AUTH is truthy AND CLAUDE_CODE_REMOTE=true; then, for a provider with no real key in the environment, the SDK gets the fixed non-secret placeholder `legalmcp-cloud-proxy-auth-placeholder` and the proxy injects the real credential. A real key in the environment or .env always wins; without the flag behaviour is exactly the local one (missing key = error). system_health reports `proxy_auth_enabled` and `provider_key_source` (env / proxy_placeholder / none) per provider, never values. The `*_key_configured` fields keep their meaning: a real key in the environment.

gemini_review has an optional allow_fallback (default true = previous behaviour). allow_fallback=false returns a transient Gemini failure as an error instead of calling OpenAI.

Gemini output budget: in the Gemini API max_output_tokens includes the model's internal thinking, so a small cap used to give HTTP 200 with an empty or cut-off text. For depth=standard gemini_review and the Gemini leg of ai_compare now use thinking_level=low (override: GEMINI_STANDARD_THINKING_LEVEL = minimal|low|medium|high) and raise any max_output_tokens below 2048 to 2048 (ceiling 8000); deep keeps thinking_level=high and its previous floor. Only thinking_level is sent, never thinking_budget. A response is a successful review only if the text is non-empty and finish_reason is STOP (or not reported): empty text -> success=false, error_type=EmptyResponse; MAX_TOKENS or another non-STOP finish -> success=false, error_type=IncompleteResponse; both carry incomplete=true, finish_reason, usage (incl. thinking_tokens), output_budget and a hint, and a cut-off text is returned as partial_review, never as review. ai_compare reports it as gemini_incomplete_response and does not count it as an independent review.

Completeness of every review (OpenAI, DeepSeek, Gemini): HTTP 200 is not a review. One helper, assess_review_completion, reads the existing adapter helpers: OpenAI Responses status / incomplete_details (status!=completed, e.g. incomplete: max_output_tokens), DeepSeek finish_reason (length, content_filter, ...) and empty content, Gemini finish_reason and empty text. Anything not complete returns success=false, incomplete=true, incomplete_status (empty|truncated|incomplete), error_type EmptyResponse|IncompleteResponse, finish_reason, usage, output_budget, a hint and, if any text exists, partial_review (never review). It applies to ai_review, deepseek_review, gemini_review (also its OpenAI fallback) and the OpenAI/Gemini legs of ai_compare, which do not count such an answer as an independent review. A finish the SDK did not report is not treated as truncation. Tool signatures and the local mode are unchanged. ai_compare covers OpenAI and Gemini only; DeepSeek is a separate deepseek_review call.

MCP tool-call timeout: .mcp.json sets "timeout": 180000 (ms) for LegalMCP. Per the Claude Code MCP docs this per-server field is the wall-clock limit of one tool call and overrides MCP_TOOL_TIMEOUT (it is separate from MCP_TIMEOUT, which is the startup limit). It lets a slow review finish inside the client limit; it does not fix provider 5xx errors. Validated offline only (test_mcp_config.py); enforcement by the client needs a native call longer than the old limit.

Cloud fallback for legal_collect_section (zakon.rada.gov.ua): in a cloud session the browser can get HTTP 502 ("upstream request failed") for a document page. ONLY when CLAUDE_CODE_REMOTE=true, ONLY for the exact current-document URL https://zakon.rada.gov.ua/laws/show/<id> (optional plain #fragment), and ONLY after the browser has demonstrably failed (HTTP >= 400, navigation error, or an empty page under 200 characters), the tool reads the official "Текст для друку" page of the same document once: curl via an argv list (no shell; -q, --proto =https, --max-redirs 0, 60 s, 16 MB, no headers/cookies/keys, default TLS verification) from the same host, with the same proxy and CA settings as the rest of the session; no new network permission. The page is cut into article blocks with the stdlib HTMLParser by the same rules as the browser extractor. HTTP 200 alone is not enough: the start must be a heading/paragraph block with the site's paragraph anchor (a name=nNNN) and the end must be a confirmed boundary (next "Стаття N" heading or end_text); an unknown, unbounded or limit-truncated section is a failure, never a success. Dated editions (/ed...), /print, /paran, queries, other hosts and ids outside the supported patterns are refused, so a historical text is never replaced by the current one; start_selector is not supported by the fallback. The record has the usual legal_section fields plus requested_url, source_url (=/print), retrieval_method=http_print_fallback, fallback_used, fallback_reason, boundary, response_bytes, edition_verified=false and an edition note: the edition is NOT verified automatically. Outside a cloud session, or when the browser works, nothing changes. Tool parameters of the 20 original tools are unchanged.

Gemini API mode: GEMINI_API_MODE=generate_content (default, google-genai SDK generate_content, unchanged) or interactions (async POST https://generativelanguage.googleapis.com/v1beta/interactions). Only the project cloud MCP env (.mcp.json) turns interactions on; launch.sh, setup.sh, local .env and local keys are untouched, and an unknown value is an error rather than a silent default. Interactions uses plain async httpx with the existing x-goog-api-key (real key, or the cloud proxy-auth placeholder replaced by the proxy), default TLS verification, no redirects, store=false, background=false, stream=false, no tools; the whole system instruction and input are sent exactly as in the legacy path; thinking_level is low (standard) or high (deep) - minimal is not supported by gemini-3.8-flash and is mapped to low. It runs inside the existing retry/deadline layer (3 attempts, 60 s per attempt, 120 s total, no nested retries) and the transport is closed after every attempt or cancellation. Completeness follows the Interactions status: only status=completed with non-empty text in the single final model_output step is a review; incomplete (max tokens), budget_exceeded, requires_action, failed, cancelled, queued, in_progress, unknown or missing status, thought-only, empty, tool-call/result or other unexpected steps, a second model_output, a non-text block, or step/interaction errors are honest failures (success=false, incomplete=true, partial_review only for a non-final text, never review). The real status is returned as interaction_status, no finish_reason is invented (it stays null), usage is mapped from total_input/output/thought/total tokens, 429/5xx are classified by HTTP status, and keys never appear in errors (exact-key and key-shaped values are scrubbed). api_mode and transport are explicit in gemini_review and in the Gemini leg of ai_compare; switching API is not a provider substitution, and allow_fallback=false still forbids the OpenAI fallback (a fallback result is labelled api_mode=openai_responses, primary_api_mode=interactions). system_health reports gemini_api_mode. httpx is a transitive dependency of the pinned openai and google-genai packages and is not pinned separately. Tests: `.venv/bin/python -B tools/legalmcp/test_gemini_interactions.py` (offline, 97 tests, httpx MockTransport). Hardening (stage 9): provider `error.code` is scrubbed like `message`; a non-list/malformed step `content` is a `malformed_response`, never success; `actual_model` is the model really returned in the response (`model_check` = confirmed/mismatch/missing/unchecked; mismatch or missing gives `status=model_unconfirmed`, no `review`, independent check not confirmed); a 429 that unambiguously reports a daily quota (per day / daily / Free Tier with Retry-After >= 1 h) is not retried (`quota_exhausted=true`, `quota_scope=daily`, `retryable=false`, one POST), an ordinary 429 keeps the bounded retry, and a Retry-After that does not fit in the remaining 120 s deadline suppresses the retry (Gemini only).

Grok creative critic (grok_critic.py, tools grok_review and grok_status). Role: independent critic of advertising ideas, positioning, copy and scripts; it receives the material only, never other models' reviews, and is not started automatically for legal or code tasks. The final decision is Claude's, by evidence, not by vote. One text request per call to POST https://api.x.ai/v1/responses (Responses API, strict structured output via text.format json_schema, store=false, system + user input messages); no web/X search, no tools, no media generation, no retries, no fallback and no substitution of model or provider. Model: grok-4.7 by default, override only with GROK_REVIEW_MODEL (must be a grok-* ID); if it is unavailable the call fails (HTTP 404 -> model_or_endpoint_not_found, a different returned model -> model_mismatch) and nothing is substituted. grok-4.7 always reasons and reasoning tokens count against max_output_tokens, so the effort is explicit: GROK_REASONING_EFFORT = low (default) | medium | high | xhigh; a small cap with high effort can end as incomplete. Key: XAI_API_KEY from the environment, or in the explicit proxy-auth mode the same non-secret placeholder as for the other providers (the network proxy injects Authorization for api.x.ai, path /v1/); the key is never read from the proxy, logged or returned. A review is success=true and incomplete=false only if status=completed, the message is completed, no refusal, the returned model equals the requested one (or a dated alias), and the JSON matches the eight-field schema (verdict, strengths, weaknesses, alternatives, concrete_edits, claims_to_verify, missing_information, test_plan) with at least one non-empty list; anything else is an error (incomplete_response with incomplete_reason, refused, invalid_review_json/schema, model_mismatch, response_too_large) and carries no review. HTTP errors are returned as authentication_error (401/403), rate_limited (429, including quota), model_or_endpoint_not_found (404), provider_unavailable (5xx), request_rejected (other), timeout, network_error; provider bodies are never returned. The result has requested/actual provider and model, fallback_used=false, attempts_used, reasoning_effort, usage (input/output/total/reasoning tokens and the provider's cost_in_usd_ticks counter) and key_source; actual_provider is null until a provider answer was received. grok_status and system_health (xai_key_configured and the grok_critic block with model, effort and key_source; provider_key_source keeps its three original entries) are configuration only: they do not test API access or billing. Offline tests do not prove a live call.
