# Как развивать маркетинговую работу оркестра

Версия 14.10.2026. Эта методика повторного использования знаний не запускает задачи сама и не меняет разрешения.

## Цикл

Вопрос → первоисточник → ограниченное утверждение → гипотеза для проекта → материал → наблюдение → решение → сохранённое исправление.

Карточка знания должна содержать источник, дату, проект, само утверждение, границы применимости и способ повторной проверки. Перенос между проектами требует нового применения: аудитория GrantPlan не является аудиторией любого будущего бизнеса.

Отдельно хранить:

- Факт платформы: например, тип ссылки в Shorts.
- Гипотезу: сценарий с поворотом может лучше удерживать внимание.
- Результат: измеренные данные конкретного периода.
- Исправление: какую прежнюю ошибку устранили и чем проверили.

## Роли

| Роль | Результат |
| --- | --- |
| Координатор, включая Claude при фактическом подключении | Ясная задача, ограничения, сопоставление выводов |
| Исследователь | Первичные источники и подтверждённые положения |
| Креативный критик, например Grok | Независимые варианты и сомнения |
| Аналитик | Воронка, экономика, качество данных |
| Редактор | Понятный текст и соответствие обещания продукту |
| Разработчик | Проверенная реализация измерения и страниц |

Модель получает роль по задаче, а не считается компетентной из-за названия. Ответ Claude как аналитика и наличие у него нативных MCP-инструментов — разные проверяемые факты.

В этом пакете платные рецензии не выполнялись. Источники проверены исполнителем; коллективного одобрения нет. Отдельный успешно запущенный MCP-процесс не подтверждает инструменты текущего чата.

## Промпт для следующей независимой рецензии

```text
Проект: GrantPlan, подготовка бизнес-планов и расчётов по Украине.
Режим сейчас: бесплатное продвижение через поиск Google и YouTube.
Задача: независимо оценить приложенный материал как маркетолог,
редактор и аналитик продаж. Не вызывать другие модели и не публиковать.
Факты с источниками отделить от гипотез и придуманных примеров.
Проверить: конкретность предложения; путь до заявки; соответствие CTA
формату Shorts; убедительность без неподтверждённых обещаний;
экономику с корректными знаменателями; измеримость; приватность.
Дай до 5 существенных замечаний: проблема, почему важна,
точная правка, способ проверить. Если факта не хватает — вопрос,
а не придуманная статистика. Отдельно предложи 2 ярких сюжетных
варианта с мягким юмором. Не переписывай всё ради стилистики.
Укажи actual provider/model и полноту ответа, если они доступны.
```

Перед API-рецензией проверять лимит вызовов и резервировать запрос через AI Orchestra. При исчерпании лимита остановить вызовы; не обходить лимит другим клиентом. Рецензенты не видят выводов друг друга. Несогласие разрешается источником или наблюдением, а не голосованием.

## Что автоматизировать следующим

1. Проверку ссылок и дат источников, без автоматического принятия изменённого текста.
2. Подготовку черновика недельного отчёта из доступных агрегатов.
3. Напоминание о незакрытых гипотезах; уведомлять по изменению результата.
4. Сопоставление подтверждённых заявок и сделок в приватном процессе.
5. Денежную проверку до платного запроса или кампании.

Для каждого шага сначала критерии, локальная проверка и ограничение доступа. Это дорожная карта; перечисленные подключения не установлены этим пакетом.

- Google Search Central: технические основы и критерии содержательной пользы — S01–S04.
- Google Analytics Help: кампания, лиды, качество и ограничения данных — S05–S08.
- YouTube Help: путь просмотра и метрики Shorts — S09–S13.
- Публичная программа [HubSpot Inbound Sales](https://academy.hubspot.com/courses/inbound-sales) — бесплатный курс по продаже через понимание задачи клиента.
- [YC: общение с ранними клиентами](https://www.ycombinator.com/library/IP-dalton-michael-secrets-you-can-learn-from-your-customers) — материал для подготовки интервью.
